# YARD READY — CY 배치 지원 데모

> 기존 운송·선박·터미널 정보를 활용해 도착 불확실성에 따른 최초 적치와 선택적 선작업 대안을 제시하고, 현장 관리자가 승인한 결과를 기록하는 AI 의사결정 지원 모듈입니다.

수출 FCL 컨테이너의 반입 예약·운송 진행(올컨e 기존 정보), 선박 일정(Port-i 모의), TOS 장치 상태(모의)를 연결해
도착이 늦어지는 트럭을 미리 알고, 플래너가 근거를 보고 승인하면 추가 이동이 줄어드는 흐름을 보여주는 Streamlit 데모입니다.
**모든 데이터는 시드를 고정한 합성 데이터이며 부산항 실제 성과가 아닙니다.** 앱 이름은 `config/params.yaml`의 `app_name` 하나로 바꿀 수 있습니다.

## 실행 방법

```bash
cd yard-ready
python -m pip install -r requirements.txt
python -m pytest            # 계산 로직 테스트 (26개)
streamlit run app.py        # http://localhost:8501
```

- Python 3.11 이상, 외부 API·키 없이 오프라인으로 실행됩니다(글꼴만 CDN에서 받고, 없으면 시스템 글꼴로 대체).
- 첫 실행 때 합성 이력 60일로 ETA 모델(기준모형 + GBM)을 학습·검증하므로 10초 정도 걸립니다.
- 효과 비교의 조건별 히트맵은 `data/experiment_grid.csv`를 읽습니다. 다시 만들려면:
  ```bash
  python -m core.experiment --full      # 36개 조건 × 시드 10개, 약 5분
  ```
- **Streamlit Community Cloud 배포:** 저장소를 GitHub에 올린 뒤 share.streamlit.io에서 `app.py`를 진입점으로 지정합니다(계정이 필요해 이 저장소에서는 배포하지 않았습니다).
- **오프라인 백업:** 시연장 네트워크가 불안하면 노트북에서 `streamlit run app.py`로 띄우고, 아래 캡처 목록을 미리 찍어 둡니다.

## 3분 시연 순서 (S1 기준)

사이드바 시나리오는 **S1 · 대표: 도착 지연 × 선적 상위**, 역할은 **야드 플래너**로 둡니다. 앱은 첫 사건(13:35 ETA 갱신)까지 재생한 상태로 열립니다.

| 단계 | 시간 | 화면 | 할 일 · 보여줄 것 |
| --- | --- | --- | --- |
| 1 | 30초 | 통합 관제 | 시뮬레이션 시각 13:35, KPI 4장. "검토 필요 3건"에서 **HMMU1234567**(지연 · 선적 상위)의 **검토하기**를 누릅니다. |
| 2 | 30초 | 도착·변경 분석 | 예약 14:00 → ETA 14:20~14:40으로 갱신된 타임라인. 반입 마감 15:00, 선박 작업 16:00과 겹치는 점을 설명합니다. **CY 배치 대안 보기 →** |
| 3 | 60초 | CY 배치 대안 | 기본 보기 **A 적용 후 예상**: 현재 계획대로면 대상(흰 테두리) 위에 그룹 2가 쌓입니다(표본 200개 중 178개). 카드 비교: A 10.0회, **B1 8.0회(−2.0, 추천)**, B2 9.0회, C 9.0회(선작업 3 + 재취급 6). **3D 보기** 토글을 한 번 켭니다. |
| 4 | 20초 | CY 배치 대안 → 올컨e 기사 화면 | **승인** → 사유 "추천 근거에 동의" → 확정. 올컨e 미리보기에 "A블록 4레인으로 진입해 주세요"가 뜹니다. |
| 5 | 20초 | 승인·작업 이력 | 사이드바 **▶ 다음**을 두 번(13:50 → 14:31 게이트 도착), 한 번 더(16:00 인출 시작). 이력에 예상 8.0회(시안)와 실제 8회(보라)가 나란히 기록됩니다. |
| 6 | 20초 | 효과 비교 | 미리 계산한 결과(보통 · ×1.0): 기준 12.5 → 제안 6.7회/100개, **악화된 실행 1/10회**를 함께 보여줍니다. 히트맵에서 조건별 감소율을 짚습니다. |

시간이 남으면 시나리오를 **S2**로 바꿔 CY 배치 대안에서 "예측 구간이 100분으로 넓어 선작업 추천을 보류합니다" 장면을 10초 보여줍니다.
S4에서는 13:35 추천을 만든 뒤 ▶ 다음(13:40 작업계획 v4)을 누르면 "만료" 배지와 **다시 계산** 버튼, 다시 계산한 추천의 "예외 검토" 배너가 나옵니다.

## 정책 비교 결과 (합성 환경, 시드 10개, 긴급 작업 없음)

총 추가 이동/100개 = (선작업 + 작업 중 재취급) ÷ 공통 평가 대상 × 100, V1 구역, 06:00~V1 인출 시작.

| 장치율 | ETA 오차 | 계획 변경 | 기준 | 제안 | 감소율 | 악화된 실행 | 미완료(기준/제안) |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 낮음 | ×1.0 | 없음 | 13.3 | 8.9 | +33% | 1/10 | 0 / 0 |
| 보통 | ×1.0 | 없음 | 12.5 | 6.7 | +47% | 1/10 | 0 / 0 |
| 보통 | ×1.0 | 있음 | 22.3 | 16.8 | +25% | 1/10 | 0 / 0 |
| 보통 | ×2.0 | 있음 | 20.3 | 16.9 | +16% | 2/10 | 0 / 0 |
| 높음 | ×1.5 | 없음 | 14.2 | 9.5 | +34% | 0/10 | 0 / 1 |
| 높음 | ×2.0 | 있음 | 21.9 | 19.6 | +11% | 3/10 | 0 / 1 |

전체 36개 조건 × 10시드 = 360회 중 **41회는 제안 정책이 더 나빴고**, 제안 정책에서만 미완료 작업(구역 만석) 10건이 나왔습니다(미리 예약한 칸 때문에 다른 컨테이너가 놓을 곳을 잃은 경우). 수치는 조정하지 않았습니다.
이 감소율은 공개한 단순 기준 정책 대비 합성 환경 값이며, 기획서의 "총 추가 이동/100개 10% 감소"(실증 잠정 목표)와 다른 값입니다. 시뮬레이션 감소율을 실증 예상치로 쓰지 않습니다.

```text

core/premarshal.py         유휴 시간 선작업(최대 3회)
core/engine.py             사건 재생, 계획 버전, 추천 만료·승인 차단, 예외, 실행 기록
core/policies.py           기준 정책 / 제안 정책
core/metrics.py · experiment.py   성과지표, 정책 비교 격자
core/audit.py              승인·보류·만료 로그
ui/                        테마·KPI·칩(components), 2D 단면·3D(yard_view), 세션(state)
pages/1~7                  통합 관제 → 도착·변경 분석 → CY 배치 대안 → 승인·작업 이력 → 효과 비교 → 올컨e 기사 화면 → 데이터·가정·한계
tests/                     재취급 3×3 손계산, 제약, 시간 누수, 보류 4종, 만료·승인 차단, 예외, 재현성
```

## 주요 가정 (자세한 값은 params.yaml)

- 블록 1개(베이 8 × 로우 6 × 단 5), 선박 2척(V1 베이 01~04, V2 05~08), 모두 40ft 일반 드라이 FCL.
- 인출 그룹은 선박 작업 10시간 전(작업계획 v2)에 배정되고, 그 전에 들어온 컨테이너는 그룹을 모른 채 쌓였다고 봅니다. 기준 정책의 재취급은 주로 여기서 생깁니다.
- 같은 그룹 컨테이너가 위에 있으면 순번을 바꿔 먼저 인출합니다(재취급 아님).
- 여유 스택 규칙은 베이마다 빈 스택 1개를 남기는 것으로 해석했습니다.
- 대안 비교 값은 대상 컨테이너 하나가 아니라 **V1 구역 인출 전체**의 예상 추가 이동입니다. 대안끼리는 같은 표본을 쓰므로 차이가 대안의 효과입니다.
- 점수 = E[선작업 + 재취급] + 0.1 × E[공급 지연(분)], 공급 지연 = 재취급 × 2.5분. 그래서 선작업 n회와 재취급 n회가 같을 때는 유휴 시간에 하는 선작업을 조금 더 낫게 봅니다.
- 자동 정책 비교는 속도 때문에 표본 6개·4시간 앞까지만 봅니다.
- 시나리오 시드 26은 S1 상황(현재 계획대로면 대상이 묻히는 야드)이 나오는 시드를 골랐습니다. 추천 결과는 그 야드에서 계산한 값 그대로입니다.
